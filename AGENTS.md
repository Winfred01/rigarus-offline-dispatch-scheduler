# Rigarus repository instructions

- Read `docs/00-PROJECT-PLAN.md`, `docs/09-DELIVERY-PLAYBOOK.md`, the current milestone and linked Issue before changing code. Check `docs/10-CLIENT-DECISIONS.md` and current acceptance evidence for any affected rule.
- Keep work to one approved vertical slice. Use one short-lived branch and one PR per Issue after the initial M0 commit. Keep `main` buildable. Require human review before merge and explicit approval before publishing a GitHub Release.
- Keep runtime Windows-only, single-operator and offline, with local SQLite. Keep scheduling rules separate from UI and persistence. Option C produces proposals for operator approval. Preserve locks and hard publishing constraints.
- Use synthetic data in source, tests, CI, screenshots and GitHub. Keep real business data, original spreadsheets and PDFs, chat exports, database files, local diagnostics and backups on authorized local systems.
- Run locked restore, format, Windows build, tests and the staged privacy scan. State the GUI and offline test conditions precisely. Record migration and regression evidence for data changes.
- Record unsettled business defaults in the decisions register or an ADR. Record client acceptance separately from engineering verification and production readiness.

## Mandatory Design-First workflow

These requirements apply at the start of every Issue implementation and every resumed implementation session. Use [the development checklist](docs/DEV-DESIGN-CHECKLIST.md) to record the evidence. Prior chats, memory, README claims and previous checklists do not replace current inspection.

1. **Read the current sources again.** Read `docs/00-PROJECT-PLAN.md`, `docs/09-DELIVERY-PLAYBOOK.md`, `docs/02-ARCHITECTURE.md`, `docs/03-DATA-MODEL.md`, `docs/05-DEMO-ACCEPTANCE.md` and `docs/10-CLIENT-DECISIONS.md`, the current milestone, affected acceptance records/ADRs and the UI design sections relevant to the Issue. Before UI development, inspect the corresponding page and original figure, including its explanatory text and corrections. For a task without UI impact, state why UI sections are not applicable.
2. **Verify source identity each time.** Check existence, declared version/date, last modification time (UTC) and current Git revision for every required file. For an external/local-only design, also record its SHA-256 and accessible location in local evidence. Git checkout times and DOCX core properties can be misleading; record them without treating them as business authority. Never skip a read because the file was read in another chat. Recheck changed sources before resuming dependent implementation.
3. **Verify the live implementation baseline.** Confirm repository identity and visibility, fetch and record latest `origin/main`, inspect the working tree, current Issue and dependencies, linked PRs/reviews/CI, and current code/tests. Preserve unrelated local changes and use an isolated worktree. Reuse the Issue branch and Draft PR when continuing it; do not duplicate merged or in-progress work based on an old plan.
4. **Output a Design Compliance Checklist before implementation.** Cite exact document sections, page/figure locators and original images inspected; distinguish concepts from implemented screenshots. Map each requirement to existing code, the needed change and an acceptance case. Record confirmed/proposed/open rules, missing sources, design differences, conflicts and decision owners. Do not invent page numbers or claim an unread source was reviewed.
5. **Output an Implementation Plan before changing product code.** Specify the files, scope boundaries, UI states and interactions (including loading, empty, invalid, failure, success, keyboard and focus behavior), API contracts, domain/persistence impact, migrations or explicit absence of them, compatibility/recovery, tests and risks. Update the plan and checklist when scope or authoritative evidence changes, before making the affected change.
6. **Respect decision authority and invariants.** Apply the latest explicitly confirmed customer/owner decision for the affected rule and cite its source/date. A newer filename, mockup, example value or Issue suggestion alone does not confirm a business rule. Do not turn unconfirmed requirements into new mandatory fields or hard constraints. Preserve existing database/domain invariants until an approved change and migration say otherwise; an open question is not permission to remove a constraint. Record unsettled defaults in `docs/10-CLIENT-DECISIONS.md` or an ADR. Resolve material conflicts with the decision owner before affected implementation.
7. **Keep the selected stack.** New product work uses Tauri, React/TypeScript, Python FastAPI and local SQLite. Keep scheduling/domain rules separate from UI, HTTP and persistence. WPF/.NET is a historical behavior and SQLite compatibility baseline; do not restore it as the architecture for new features. Keep Windows-only, single-operator offline operation, Option C operator approval, locks and hard publication constraints.
8. **Compare and test the implemented UI.** After UI changes, compare actual screenshots and interaction states with the cited design pages/figures and document intentional differences. Test relevant normal, boundary, error, keyboard/focus, accessibility and responsive behavior. Exercise the packaged Windows desktop and offline flow where applicable; record actual OS, package/commit/hash, network condition and limitations. Browser checks, CI and concept images are not evidence of a native/offline GUI pass.
9. **Deliver one reviewed slice.** Use one feature branch and one PR per Issue (reuse both across days), run the applicable locked restores, format checks, Windows builds, tests, Windows CI and staged privacy scan. Record commands and actual PASS / FAIL / BLOCKED / NOT RUN outcomes with evidence. A documentation-only change may mark product builds/GUI checks not applicable with a reason; run documentation/privacy checks and report repository CI honestly. Do not claim completion of a failing or pending gate. Create or update a Draft PR for human review.
10. **Preserve human and data boundaries.** Do not automatically merge, publish a release, close an Issue or edit a real customer database. Releases need separate explicit approval. Never upload customer data, original customer Excel/PDF files, personnel details, credentials, raw diagnostics or backups to GitHub. Use synthetic fixtures and sanitized evidence only. Check repository visibility before any upload; a private-repository authorization does not authorize publication. Keep the complete UI DOCX local under the owner's current instruction. Do not force-add it past `.gitignore` or weaken privacy checks. Any future repository copy at `docs/design/Rigarus_UI_Design.docx` requires accessible provenance, sanitization and explicit authorization appropriate to the then-current visibility.
11. **Stop the affected work when evidence is missing.** If a critical design is missing/inaccessible or a conflict would change a business rule, mark the affected requirement BLOCKED and report the exact expected/local path, missing section or conflicting sources and the decision needed. Search accessible workspace locations before declaring it missing. A checklist or sanitized summary is not a replacement for required original UI pages. Continue only independent authorized discovery, documentation or validation; do not guess a UI specification. Do not use the missing canonical DOCX path to claim the local source is absent when it is accessible.
12. **Report traceable results every time.** The final report must list documents actually read with versions/revisions, implemented files/requirements, unmet design items, test outcomes and conditions, branch/commit/Draft PR links, remaining questions/blockers and next steps. Report engineering verification, customer acceptance and production approval separately. Keep machine-specific paths and raw evidence local; provide only sanitized locators in GitHub records.
