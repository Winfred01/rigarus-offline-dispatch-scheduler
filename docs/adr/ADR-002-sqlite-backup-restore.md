# ADR 002 — Consistent local SQLite backup and recoverable restore

**Status** Proposed for Demo A engineering review in [#10](https://github.com/Winfred01/rigarus-offline-dispatch-scheduler/issues/10). Implementation and the installed Windows recovery exercise are tracked in [#34](https://github.com/Winfred01/rigarus-offline-dispatch-scheduler/issues/34).

## Baseline and paths

The Tauri desktop starts the Python sidecar against the same per-user SQLite path as the earlier WPF application. The current backend enables WAL and checks the exact supported sequences in __EFMigrationsHistory. An initial-demo database upgrades to the Project Master schema in a transaction. The latest schema in this baseline has DemoProjects, Projects and WorkItems. The acceptance scripts use a separate synthetic profile root. Preserve those properties when adding backup and recovery.

| Relative to %LOCALAPPDATA%\RigarusDispatch | Purpose |
| --- | --- |
| data\rigarus.db | Authoritative SQLite database. SQLite manages its WAL and shared-memory files. |
| attachments\ | Proposed location for application-managed attachments. Store references as relative paths or stable IDs. |
| logs\ | Local diagnostic events. Keep these outside the archive. |
| backups\ | Proposed local default for completed backups and pre-restore or pre-upgrade safety copies. Operators can select a local or removable destination for backup exports. |
| recovery\ | Proposed same-volume restore staging, rollback files and recovery journal. Restrict to the current Windows account. |

Use Windows profile directory resolution. Reject network and synchronized destinations for managed recovery data. The app stores no data about the operator's identity in the archive manifest. A local recovery copy helps undo a failed operation. A copy on separate media also covers loss of the original disk.

## Backup

1. Serialize backup, restore, upgrade and attachment mutations through the application. Before capturing, pause writes that change database records or attachment bytes and drain pending writes. Keep that barrier until the database snapshot and referenced attachments have been copied. The maintenance mechanism also prevents a legacy WPF process or a second desktop from writing through a different connection during capture. If exclusive maintenance cannot be established against another supported writer, abort and ask the operator to close it. A mutex acquired by Tauri alone cannot coordinate a legacy process.
2. Use Python SQLite's Connection.backup on a source connection opened against the existing database, with a temporary destination connection, a progress callback, bounded lock retries and a deadline. The SQLite backup reads committed WAL content. Never copy an open database file by itself or ship its WAL/SHM files. Preserve the SQLite schema, migration IDs, row IDs and sequences. See the [SQLite Online Backup API](https://sqlite.org/backup.html).
3. Close the destination connection. Verify the staged database opens on its own with PRAGMA integrity_check returning ok and PRAGMA foreign_key_check returning zero rows. Enumerate references from that snapshot. Copy every referenced attachment and fail if a required file is missing. The current schema yields an empty attachment list. Retain data relationships and inclusion decisions as the later schema evolves.
4. Write a ZIP to a unique partial filename in the selected destination directory. The proposed manifest contains an archive format version, UTC creation time, source application version and build commit, SQLite migration sequence, and a sorted list of exact relative paths, byte lengths and SHA-256 digests. The fixed database member is data/rigarus.db. Attachment members belong below attachments/. Require manifest and database exactly once and match the member list in both directions. Hashes detect accidental corruption. Trusted origin and operator authorization are independent checks.
5. Reopen and verify the staged ZIP against its manifest. Flush and close it before publishing under a new final name on the same volume. Preserve existing completed backups on failure or retry and keep incomplete files out of the restore picker. Never include diagnostics, exported reports or raw import sources. Keep backups, recovery files and original documents on authorized local systems.

## Restore and startup recovery

1. With the operator's explicit approval, enter maintenance mode, block new writes and stop the FastAPI sidecar. Close every supported process and database handle using the target data root. Confirm the target is suitable for the coordinated local replacement operations. Check that the working volume can hold staged data and the complete rollback copy, including attachments. Use an isolated profile root for the cross-machine or cross-account engineering exercise.
2. Validate the archive before touching the live data. Apply bounded extraction limits for file count, total uncompressed bytes and maximum member size. Compare each member with the manifest. Reject absolute or parent-relative paths, alternate data streams, duplicate or case-colliding paths, wrong roots, links and reparse points. Extract to a fresh staging directory and hash files while writing. Verify SQLite integrity, foreign keys, expected schema and attachment references on the staged copy. If the archive comes from another schema version, use the compatibility rules below.
3. Create and verify a separate pre-restore safety backup of the target. For an existing database, end writes, complete a checked SQLite WAL checkpoint, close handles and confirm any old journal state can be retired safely. An incomplete checkpoint or held handle stops restore before replacement. Keep recovery files on the local target volume. Record a durable journal with the phase and original/staged/rollback locations or IDs, using paths relative to the approved profile root.
4. Publish the staged database using a same-volume Windows replacement with rollback names. Rename managed attachment directories on the same volume under the same journal. Treat the earlier database, attachments and associated SQLite state as one unit. Each step must be individually recoverable. Keep the runtime closed between steps. Flush staged content and persist each journal transition before advancing. A multi-file sequence can be interrupted between operations, so startup must resolve the journal before opening SQLite. See [Windows file replacement behavior](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).
5. Repeat integrity, foreign-key, schema and attachment checks against the activated set while writes are still disabled. Mark the journal committed only after validation. If anything fails before commit, restore the original set from the recorded rollback locations and verify it before re-enabling writes. Recovery after process or machine interruption must be idempotent. With an incomplete journal, inspect the actual names and contents before any rename so interrupted replacements are detected. If no complete set can be verified, keep both copies, block writable startup and show the operator a recovery message. Never silently initialize a new database in that state.

Use local diagnostic events for phase, stable failure code, elapsed time and recovery outcome. Include neither business values and attachment names nor destination paths in shared evidence.

## Compatibility and upgrades

- The manifest records both archive format and database migration identity. Compare it with the database's actual migration history using a read-only check. For current WPF/Tauri versions this means the ordered __EFMigrationsHistory IDs, not PRAGMA schema_version, which is SQLite's internal schema-change counter.
- Accept only archive formats and database schema sequences the installed app explicitly supports. Validate the current schema directly. Run the existing migration on a staged copy of an explicitly supported older schema and repeat all checks before promotion. Reject newer or unknown versions and missing or inconsistent migration history. Do not relabel a newer database or drop history to force a restore.
- Before an in-place app upgrade that changes the schema, close writers and complete a verified pre-upgrade backup independently of the installer. On migration failure keep the previous database or restore it using the same maintenance and journal procedure. Test the rollback with the earlier compatible application build against the original schema. Keep the original pre-upgrade backup through upgrade verification.
- **Needs customer decision before RC**. Confirm archive encryption, removable-media handling, reminder cadence, retention, purge and recovery-key ownership if encryption is selected. Technical defaults for isolated synthetic testing may use an unencrypted ZIP and retain safety backups. Set no production encryption or retention policy here.

## #34 execution matrix

Use the installed Windows x64 app in a disposable offline VM and a second isolated VM or Windows profile. Populate only fictional records and attachments. Capture source and target builds, schema IDs, manifest hashes, record IDs and reference checks. Compare the recovery outcome after relaunch. Repeat each failed restore against a fresh target copy and verify the pre-test active dataset remains intact.

| Test | Setup and action | Expected proof |
| --- | --- | --- |
| WAL and concurrent operation | Enable WAL, disable auto-checkpoint for the fixture, hold a reader and commit a new record from another connection. Back up through the SQLite API. Attempt a guarded write or second maintenance operation during capture. | Snapshot contains the committed WAL record and stable IDs. It opens on its own. Guarded writes are rejected or safely held. A deadline or lock failure produces no final archive. |
| Offline round trip | Create a synthetic note, project and related work item. At M7 include Crew, schedule, published snapshot and referenced attachment fixtures as supported. Back up and restore to the second isolated environment, then reopen. | Both integrity checks pass. IDs, relationships, values and attachment hashes match. Publication snapshots remain intact. |
| Missing input and tampering | Remove a referenced attachment, truncate an archive, modify a member, change a hash, add a duplicate member or include a path outside the allowlisted roots. | Backup or restore rejects the input before publishing or replacing active data. Prior archive and live data remain readable. |
| Schema and upgrade | Restore synthetic initial-demo and Project Master archives, then try an unknown or newer schema and a mismatched manifest. Inject failure in the supported migration and retry. | Supported versions preserve existing records. Migration and retry yield the supported history. Failed or incompatible restore leaves the target untouched. A pre-upgrade backup opens in the earlier compatible build. |
| Storage and permissions | Use an isolated low-space volume, read-only destination, disconnected removable device or locked target file. | No new corrupt final archive, no partial active dataset and a local actionable failure event. Existing backup and target remain usable. |
| Interrupted restore or upgrade | Interrupt before replacement, after database replacement, after attachment promotion, and after commit but before cleanup. Exercise recovery twice. | Startup recovers the complete original set before commit or the verified new set after commit. It never opens a mixed generation. Repeated recovery is safe. |
| Rollback failure | Make a required rollback file temporarily unavailable in the isolated environment. | Writable startup stays blocked. Recovery retains the available copies and reports the blocked phase. Retrying after access returns is safe. |

These are future installed-product tests. Design review, a synthetic SQLite experiment and CI can check the approach before that implementation.
